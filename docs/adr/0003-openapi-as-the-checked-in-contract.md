# 0003 — OpenAPI as the checked-in contract

- **Status:** Accepted
- **Date:** 2026-08-18

## Context

This is a **headless** blueprint: the worker (`example-service`) exposes a domain REST API — the
endpoints that sign a contract, report a handover, withdraw an application — with **no frontend in this
repo**. Whoever consumes that API (another service, a generated client in some other language, a Bruno
scenario, a colleague with `curl`) needs a description of the boundary that cannot silently drift from
the code. That boundary can be described three ways: (a) hand-write a spec and hope the code matches it;
(b) hand-write client types and hope they match the backend; (c) derive one side from the other.
Options (a) and (b) drift silently — the first symptom is a runtime 400 at the consumer. We want the
contract to be *impossible* to desync, and we want a new contributor to be able to read it without
running anything.

The same force runs the *other* direction too: the worker itself is a **consumer** of the remote CIB
seven engine's REST API, and we refuse to hand-write those calls for exactly the same reason (see the
generated engine client below and [`common-cibseven-client`](../../service/common-cibseven-client/README.md)).

## Decision

The **code is the single source of truth**, and the contract is **generated but committed** — in both
directions.

**For the API the worker exposes:**

1. **springdoc** serves a live OpenAPI document from the annotated controllers in
   `adapter/inbound/rest` (`@Operation(operationId = …)` gives each endpoint a stable, generator-friendly
   method name).
2. `OpenApiSpecExportTest` — a code generator wearing a JUnit costume — fetches `/v3/api-docs`,
   re-serialises it **deterministically** (keys sorted, fixed two-space LF indenter, trailing newline,
   `servers` block dropped so the random test port can't cause churn) and writes **`openapi/openapi.json`**
   at the repo root. It runs inside `./gradlew build`.
3. CI regenerates the spec and runs **`git diff --exit-code`** on `openapi/openapi.json` — a **drift
   gate** (`.github/workflows/pre-merge.yml`). If a controller changed and the committed spec wasn't
   updated, the build fails.

**For the engine API the worker consumes:** the typed Kotlin client in `common-cibseven-client` is
generated by the **OpenAPI Generator** from CIB seven's **official** OpenAPI document (bundled in the
`cibseven-engine-rest-openapi` artifact, pinned to the engine version so client and engine never drift).
Nothing generated there is committed — it is a build artifact — but the philosophy is identical: a typed,
generated boundary beats hand-written REST calls.

## Why generated-but-committed beats the alternatives

- **vs. hand-written spec/types:** eliminates the drift class entirely — the gate fails the PR, not the
  consumer at runtime.
- **vs. generated-at-build (not committed):** the committed `openapi/openapi.json` is reviewable in every
  PR diff (an API change is *visible*), any consumer can generate a client without booting the worker, and
  offline/agent workflows keep working. The cost — a checked-in generated file — is paid down by the drift
  gate that keeps it honest.

## Consequences

- **Positive:** one contract per boundary, each a gated mirror of the code; API changes are visible in
  review; a consumer's build is decoupled from a running worker.
- **Negative / trade-offs:** a generated file lives in git; forgetting to regenerate is an *expected*
  failure mode — the gate is what makes that safe, so it must never be disabled.
- **Neutral:** determinism is a hard requirement of the export test — any non-deterministic serialisation
  would make the gate flap.

## Implementation notes

- Operation ids are set explicitly (`@Operation(operationId = …)`) so any generated client's method names
  stay clean and stable.
- DTO date/time fields are pinned to a string shape (`@JsonFormat(shape = STRING)`) so the payload and the
  `string/date-time` the contract advertises stay in sync regardless of the Jackson default.
- The generated engine client uses the `jvm-spring-restclient` library, matching the `RestClient` the
  worker already uses to drive the remote engine; see the
  [`common-cibseven-client`](../../service/common-cibseven-client/README.md) README for the full build flow.
